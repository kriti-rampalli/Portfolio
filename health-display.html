Health Monitoring Display

A Linux-native monitoring interface developed during an aerospace internship to turn raw system data into clearer, decision-ready information for UAV operators.

My role
Solo, full-stack GUI: visual design, navigation, transformation logic, backend data handling
Timeline
Two-month internship
Platform
Linux on a Raspberry Pi 5, 18.5-inch display
Status
First-phase functionality delivered; presented to the client as built

Constraints

What the screen had to survive

The interface had to run natively on Linux, stay readable under widely varying lighting, support operators who might switch positions, and initially be navigable through only a few physical controls. An existing message parser stayed outside my scope because multiple teams depended on it.

I entered with almost no GUI-development experience, so I only implemented architecture I understood well enough to maintain and explain.

5

major interface iterations

5

expert reviewers: two pilots, two test pilots, a flight-test engineer

Decisions

Show less, so the right thing is seen first

I chose not to display every available value at once. The top level emphasizes overall state and frequently needed information, while deeper pages expose component detail and errors.

Rejected: a vertical layout. It did not fit the physical control station, so I moved to a landscape design whose primary screen supports either operator position.

Challenged: button-only input. After demonstrating how much extra navigation one mouse could add without consuming control-panel space, I received approval to include one.

Architecture

Separating reading, transformation and display

My earliest screens depended too directly on one another, which turned brittle as display logic grew and data sources changed. Splitting the app into three layers let the source change without rewriting the interface. Repeated elements and global fonts and colors were centralized, so later operator-requested revisions were quick to make.

Not accepting a value on trust

A flight-time fix

The open-source system's flight-time value could reset after a lost and restored connection. Instead, I stored the timestamp of the first received data packet and calculated elapsed time from that reference, which gave the display a more reliable number.

Evidence, stated plainly

Ongoing review came from experts (two pilots, two test pilots and a flight-test engineer). These were expert reviews, not a formal usability test, and I left before live-aircraft validation was possible.

Outcome

Delivered, documented, handed off

By the end of the internship the requested first-phase functionality was implemented, with a deployment procedure, test plan, handoff documentation and plans for later work that depended on unavailable hardware or other teams.

Recognition

Top-level management told me my program ran smoothly in the live demos, and appreciated my work, commitment and output as an intern who worked on the product for roughly two months. The project was presented directly to the client without any changes.

What I'd do next time

Keep the modular approach, but research existing aviation-interface conventions earlier so established patterns inform the first interface rather than arriving later with expert feedback.
